## What the evidence establishes

### Phase 1 · One accepted write, one refused stale append

1. **Routing and baseline.** The recorded 2026-11-25 run started a fresh, credential-free DCB context on native ARM64 with pinned Axon Server 2026.1.8 and Axon Framework/Axoniq Framework 5.4.2. The test driver, command handler and projection ran in three distinct JVMs with separate client IDs and role-specific registrations. The remote subscription returned zero before the write. [Feasibility record and transcript](../../../docs/feasibility/phase-01.md#native-arm64-proof), [integration test](../../../probe/src/integrationTest/kotlin/probe/AxonProbeTest.kt#L119-L167).
2. **Storage refusal.** The test captured an empty-history marker for the course or losing student, sent one real remote command, and then submitted a direct storage-engine append for a different student on the same course using the earlier marker. The second commit failed with `AppendEventsTransactionRejectedException`, gRPC `CANCELLED` and a `ConsistencyConditionException` cause. The same winning event ID appeared in the course, winning student, joint-tag and full-history reads. The losing student history stayed empty. This demonstrates overlap detection after a relevant commit. The second append was sequential and bypassed the command handler, so the result leaves both application races and conflict recovery unproved. [Integration test](../../../probe/src/integrationTest/kotlin/probe/AxonProbeTest.kt#L169-L221).
3. **Read-side correlation and limit.** The open subscription delivered a count of one carrying the winner’s event ID. A fresh remote query returned the same state. The probe handler requires empty relevant history and calls the storage engine directly. Its projection increments a process-local map and uses an in-memory token store. The live round trip establishes routing and event-to-query correlation under this setup. App-level decisions over existing state, persistent checkpoints and duplicate/replay behavior require separate tests. [Integration test](../../../probe/src/integrationTest/kotlin/probe/AxonProbeTest.kt#L223-L229), [probe handler](../../../probe/src/main/kotlin/probe/ProbeApplication.kt#L106-L145), [probe projection](../../../probe/src/main/kotlin/probe/ProbeProjection.kt#L30-L70).

The audit inspected existing Gradle XML, including a local probe result dated 2026-11-26 with 3 integration tests and zero failures, errors or skips. The original feasibility report supplies the evidence binding for the image, architecture and native run. AMD64 image metadata was captured in Phase 1 and runtime proof belongs to Phase 7. Phase 1 also recorded independent TypeID vectors, KDoc and Kotlin test-tool samples, plus a Paketo proof over a small static asset. These are starting points for an application storage round trip and application image build. [Feasibility record](../../../docs/feasibility/phase-01.md#secondary-checks), [AMD64 and probe retirement gate](../../../docs/feasibility/phase-01.md#hosted-amd64-verification-and-retirement).

## Acceptance criteria for the next phases

### 1. Phase 3 · Prove both enrollment boundaries (`DCB-07`, `DCB-08`, `CQRS-01`, `QA-01`)

**Command and test owners.** Run two Testcontainers races through application command handlers on the selected Axon Server. First set up one remaining seat and two eligible students. Then give one student one remaining allowance and target two courses with space. In each case, use a test barrier so both independent attempts finish reading their overlapping history before either writes. Release both and record their outcomes. Pass when exactly one new enrollment backed by a committed event carries the appropriate course and student tags, the losing attempt reaches the relevant rule rejection after a fresh read, and both projected views agree with the event history at the limit. In a disposable negative control, weaken the effective append protection for the shared boundary and show that the persisted-count assertions catch double acceptance. Account for any criteria the framework derives from the appended event tags when constructing that control. Add given–when–then cases for the capacity and allowance decisions over pre-existing events. [DCB course subscription example](https://dcb.events/examples/course-subscriptions/) · [Axon event store internals](https://docs.axoniq.io/axon-framework-reference/5.1/events/event-store-internals/).

### 2. Phase 3 · Define retry and recovery semantics (`CQRS-01`, `CQRS-02`, `QA-01`)

**Command, query and BFF owners.** Submit the same logical operation twice, then simulate a lost reply after a committed write and retry with the same operation identity. Pass when each operation has one recorded outcome and at most one business effect. Inject a confirmed consistency conflict, a transport outage and a timeout with an unknown outcome. Verify bounded conflict retry using a fresh history and a distinct API outcome for rule rejection, temporary failure and unknown write status. Decide how command identity and outcome survive the uncertain reply before exposing retry in the browser.

**Query owner.** Use a durable processor checkpoint near the PostgreSQL projection state. Interrupt processing around a projection write and checkpoint advancement, restart the query service and redeliver a previously handled event. Then rebuild the read model from committed events with an explicit replay start. Pass when the rebuilt and resumed course/student views equal the history-derived result, each event has one effective projection change, and a subscriber sees no phantom state from an uncommitted projection write. Qualify the first PostgreSQL image and resolved JDBC dependencies with the actual application runtime graphs and a real database run. [Axon token-store guidance](https://docs.axoniq.io/axon-framework-reference/5.4/tuning/event-processing/#token-store), [replay migration guidance](https://docs.axoniq.io/axon-framework-reference/5.4/migration/paths/projectors-event-processors/), [Phase 1 dependency and image review](../../../docs/feasibility/phase-01.md#dependency-and-image-review).

### 3. Phase 3 · Exercise service and browser contracts (`FND-03`, `DCB-01`, `DCB-04`–`DCB-06`, `CQRS-02`)
